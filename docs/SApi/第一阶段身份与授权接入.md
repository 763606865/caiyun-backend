# 第一阶段：统一身份与授权接入

日期：2026-11-14。本文描述代码实现与配置步骤，不代表真实环境已迁移或五系统生产联调已完成。机器可读契约见 `integration.openapi.json`。

## 已实现接口

所有 `/sapi` 路由沿用 `authentication.md` 中的 HMAC-SHA256 签名、nonce 防重放及 HTTPS；有效签名不等于具备企业目录权限。应用注册编码精确匹配（现有 Seeder 是小写 `oa/crm/erp/mes/wms`，不要把示例中的大写直接照搬）。

- `POST /sapi/directory/upserts`：源目录幂等写入；enterprise/user/organization/employment 四类。`source_system` 必须等于签名应用的注册 code。
- `GET /sapi/directory/snapshots?enterprise_uuid=...&entity_type=...`：首次获取一致快照，最多100项/页，返回 `snapshot_id/items/cursor/next_page`。后续传同一 `snapshot_id` 和 `page`，30分钟过期返回409，需重新拉快照。
- `GET /sapi/directory/changes?enterprise_uuid=...&cursor=0`：每企业游标，返回 `items/next_cursor/has_more`，每项含 `version/entity_type/entity_uuid/payload/occurred_at`；增量目前不删除、不清理，不虚构已实现的游标保留期。
- `POST /sapi/identity/resolve`：按来源稳定键精确查本应用映射，不按手机号自动匹配。
- `POST /sapi/auth/check`：真实读取企业、用户、组织、任职、应用状态和企业/任职两级应用grant；`active` 为false时应用必须撤销访问。
- `POST /api/platform/login-tickets`：真实 `auth:api` 中台用户会话，创建自己的目标应用票据；不接受调用者指定另一个用户。
- `POST /sapi/auth/exchange`：目标应用签名兑换 code；绑定应用、精确回跳地址和state，60秒有效、原子单次消费，返回统一身份及state。
- `PUT /sapi/enterprises/{enterpriseUuid}/application-grants/{applicationCode}` 及 `.../employments/{employmentUuid}/application-grants/{applicationCode}`：必须同时有 `grants.manage` 的签名应用和真实企业管理员 `auth:api` 用户会话。
- `GET /sapi/integration/status`：仅 `platform.admin` 可查应用状态、最近失败审计、来源数量与目录游标。

## 访问收紧与兼容

旧 `/sapi/users`、`/enterprises`、`/organizations` 及职工 CRUD 路径保持存在，但**仅显式 `platform.admin` 运维凭证可使用**。普通业务应用转用按企业限定的新目录接口，不向业务系统发放全量目录权限。

旧套餐路径增加 UUID 企业路径兼容：`/sapi/enterprises/{enterpriseUuid}/subscriptions`，避免先分页枚举企业再解析数字ID。普通应用必须获 `subscription.read/write`，仅可读写自己的应用套餐；数字路径仍支持。其他应用的套餐不可见、不可写。此变更须与 OA SDK 一同发布。

组织父节点必须同企业且不能成环；组织不能直接迁移到其他企业。任职 UUID 增量迁移时回填，OA 离职使用 `is_enabled=false`，不删除全局用户。

## 目录契约

请求：

```json
{
  "entity_type": "employment",
  "source_system": "oa",
  "source_id": "member:42",
  "source_version": 3,
  "enterprise_uuid": "企业统一UUID",
  "idempotency_key": "employment:42:3",
  "payload": {
    "user_uuid": "用户统一UUID",
    "organization_uuid": "部门统一UUID",
    "employee_no": "E042",
    "position": "销售",
    "is_enabled": true
  }
}
```

成功外层保持 `{code:200,data:{entity_uuid,entity_type,enterprise_uuid,version,source_version},meta:{...}}`。幂等键重试使用完全相同内容；同键不同内容409。同来源对象的 source_version 单调递增；旧版本或同版本不同内容409。不允许工资、密码、身份证等非白名单字段。

- enterprise payload：code/name（新建必填）、short_name/credit_code/contact_name/contact_mobile/is_enabled。
- user payload：phone（新建必填）、real_name/nick_name/email/status（0/1）。用户是全局身份，但写入必须提供已授权 enterprise_uuid；来源键在应用+类型中唯一，应采用稳定本地用户ID；跨企业引用通过显式映射确认。
- organization payload：code/name（新建必填）、parent_uuid/is_enabled。部门父节点须同企业，依赖缺失返回404，由源系统保留任务后重试。
- employment payload：user_uuid（新建必填）、organization_uuid/employee_no/position/is_enabled。同企业同用户只能一个任职；已有任职的用户不可被替换。

读取采用最小投影：user 不提供手机号、邮箱或密码；任职返回 user_uuid/organization_uuid/employee_no/position/is_enabled；组织返回 parent_uuid/code/name/is_enabled。每个快照 item 自带 `version=快照cursor`。四类型分别拉快照后，使用最小快照cursor追增量，避免类型快照时点差；写成功后才保存消费游标。先企业/用户、后父子组织、再任职。目录不会赋予任何业务角色。

首次新企业允许 enterprise_uuid 为空，但必须显式授 `directory.bootstrap`；只能创建新企业，不能借此绑定/接管任意已有企业。新建成功后仅对源应用增加该企业的目录读写和授权检查scope，不开通应用/任职grant。其他应用scope由运维单独配置。

## 运维配置与历史数据

先备份数据库、迁移试演练，再在计划环境执行新增migration；本机PHASE1_TEST联调已仅执行7个明确必要的历史平台前置迁移及本次新增迁移；未执行其他pending迁移，既有用户/业务数据保留。其他环境须先核对自身迁移状态。以下为示意命令，不含真实身份、地址和密钥。

```sh
# 原有应用注册、启用和凭证仍由Admin管理，密钥只保存在各后端安全配置。
php artisan platform:integration oa --scope=directory.bootstrap
php artisan platform:integration oa --enterprise=企业UUID --scope=directory.read --scope=directory.write --scope=auth.check --scope=subscription.read --scope=subscription.write
php artisan platform:integration crm --enterprise=企业UUID --scope=directory.read --scope=auth.check --redirect-uri=https://crm.example.com/integration/caiyun/callback
# 企业应用开通与人员应用授权是两项不同配置。
php artisan platform:integration crm --enterprise=企业UUID --grant
php artisan platform:integration crm --enterprise=企业UUID --employment=任职UUID --grant
# 授权撤销不删除任职/历史业务。
php artisan platform:integration crm --enterprise=企业UUID --employment=任职UUID --grant --revoke
# 历史来源映射先预检，确认后才 --apply，不按手机号自动合并。
php artisan platform:directory-bind oa user user:42 用户UUID --enterprise=企业UUID
php artisan platform:directory-bind oa user user:42 用户UUID --enterprise=企业UUID --apply
```

`platform.admin` 是全局平台运维scope，具有全量目录管理能力，不给普通应用；历史旧调用不能为了省事授全局权限。`grants.manage` 仅给可信企业授权管理应用，并仍需要真实企业管理员用户会话。

已有源映射不得覆盖到另一个统一身份。`platform:directory-bind` 默认只预检，`--apply` 才确认；它是本阶段的人工绑定入口，不宣称已经交付完整的冲突候选管理页面。登录白名单可通过既有Admin应用管理页面编辑。

## 撤权、目录变化与审计

业务应用需在60秒以内重新确认授权，不能只在登录时检查。中台不可用且校验缓存到期时必须拒绝受保护访问。已有会话也必须经过该检查，旧本地登录不能绕过。

目录upsert在事务中持久化来源版本、幂等响应和变更记录，快照与该写入互斥；失败响应不会推进来源版本。Admin/旧CRUD的模型保存/删除通过观察者补目录变化和停用墓碑；直接数据库批量SQL不触发模型事件，必须改走目录服务或显式重放，不能作为人员同步入口。财务/业务角色不由本接口管理。

有效签名调用的路径、状态、调用应用及trace_id写入审计表，票据和密钥不入日志。配置/绑定命令单独审计。新增表包含身份来源、scope、grant、幂等、目录日志、快照、票据和接入审计；保留期清理、完善可视化监控及人工候选工作台仍需发布前配置/后续增强。

## 验证

`php vendor/bin/phpunit --filter SApi --no-progress` 覆盖旧CRUD显式运维授权、默认拒绝、幂等/旧版本、快照与停用增量、组织跨企业拒绝、auth/check、票据有效期/单次消费/回跳绑定、企业管理员授权及UUID套餐隔离。测试采用SQLite内存数据库，不代表五应用真实浏览器联调通过。

## 本机试点与持续启动

本机试点仅使用 `PHASE1_TEST_*` 企业和 `phase1-oa/crm/erp/mes/wms` 专用应用，不修改既有应用密钥，不代表现有企业都已绑定或全部迁移。OA 的专用职工、部门、任职通过真实 HTTP 进入中台，再由各应用显式绑定本地身份；角色由各应用单独配置。

临时中台 HTTP 服务为本机回环 `http://127.0.0.1:19880`，它是本次联调进程，不是持久化部署。持续启动需要使用项目原有 PHP 服务/进程管理方式及安全配置；各应用持久保存自己的 endpoint/application_code/key/secret 与精确回跳地址，并按环境管理凭证，不依赖临时会话的 config 覆盖。真实部署使用 HTTPS。试点临时凭证不进入仓库，不在文档输出。

推广到其他企业前必须预检并显式绑定、配置企业scope、企业及任职两级grant和本地业务角色；每个企业单独完成验收。不能把本机专用测试通过解读为所有企业已经启用统一身份。
